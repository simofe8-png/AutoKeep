# Vehicle identification correction (2026-09-28)

The owner tested the build on his Android device and raised three issues, plus an investigation
request. This file records the findings and what changed. It does **not** declare the
vehicle-identification work PASS: the license-scan issue needs an owner decision first (§4).

## 1. Vehicle image did not match the SEAT Ibiza

**Source audit.** The app has exactly one vehicle-image source: `VehiclePhoto`
(`src/features/vehicles/VehicleVisuals.tsx`). It shows:

- the user's own photo, which is device-local (settings key `vehiclePhotos`); or
- a bundled PNG per vehicle _kind_: `assets/vehicles/{car,motorcycle,scooter}.png`, generated by
  `tools/vehicle-art.py`.

There is no network image, no provider and no model lookup.

**Root cause.**

- The bundled car art, added for screen parity, was a colored illustration of a white four-door
  sedan in a landscape.
- It filled the place where the references show _the_ vehicle's photo, and it had no label.
- It was the same for every car, so any identified car (such as a hatchback SEAT Ibiza) was
  presented with an unrelated body style and color.

**Fix.**

- The art is now a colorless two-tone silhouette on a muted scene: no body color, lights or detail.
- Hero and wide images carry the label "איור כללי · לא תמונת הרכב שלך".
- The user's own photo is preferred, and it never shows on another vehicle.
- No provider, scraper, API or dataset was added.

## 2. Color and 3. Engine code

**Model and storage.**

| Layer      | Change                                                                                                                                            |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Domain     | `VehicleIdentity.color?`, `VehicleIdentity.engineCode?`. `parseEngineCode` upper-cases and validates; a malformed code is rejected, never "fixed" |
| SQLite     | Migration v4: `vehicles.color`, `vehicles.engine_code` (nullable; existing rows keep NULL = unknown)                                              |
| Cloud      | `20260928000002_vehicle_color_engine_code.sql`: columns plus length limits. `sync_push`/`adopt_local_data` resolve columns dynamically            |
| Sync merge | Both are field-level identity fields: an edit on each of two devices keeps both                                                                   |

**Onboarding.**

- Manual entry has "קוד מנוע" (optional, with a hint; nothing is derived from the displacement)
  and "צבע" (optional).
- Either the displacement or the engine code satisfies the required "engine" fact.
- The confirm screen shows both, with their provenance.

**Registry (data.gov.il).**

- Correction: `degem_manoa` is the **engine code**. It was previously stored as the "engine"
  (displacement).
- It now maps to `engineCode`, and `tzeva_rechev` maps to `color`. The displacement is filled only
  from `nefah_manoa`/`nefach_manoa`.
- The motorcycle dataset's `mispar_manoa` is an engine _serial number_ and is deliberately not
  used.

**Provenance.**

- During onboarding, provenance is shown per field (registry / scan / user).
- The architecture does **not** persist per-field provenance on the vehicle record for any
  identity field, so none was invented for these two.
- This is a known gap for the future applicability work.

**Display.** Vehicle details show both fields when known. Garage Mode shows both in "known facts".

**Legacy data.**

- Vehicles identified through the registry before this change may hold the engine code in the
  `engine` field. For that reason the label stays the neutral "מנוע".
- Nothing is moved automatically, because that would be inference.
- There is no vehicle-edit screen yet, so such a vehicle keeps its current values.

## 4. License-camera scan: investigation (no provider-dependent change made)

**What actually happens in the release build (real data mode):**

1. **Camera.** The scan screen calls `expoAcquisition.captureWithCamera()`.
   - This is the system camera through expo-image-picker. The camera permission is requested.
   - Quality is 0.85, with no EXIF, no base64 and no crop. The gallery goes through the system
     picker.
2. **Capture.** The acquired file (URI, MIME type, size) is kept in memory in the onboarding
   context (`setAcquired`).
   - It is not stored as a document and not uploaded.
   - It is discarded when onboarding ends.
3. **Preprocessing.** None.
4. **Extraction.** `onboardingServices().extractor` is hard-wired to `null`
   (`src/features/data/dataSource.ts`, comment "G1: no OCR/AI runtime provider is approved").
   `RealIdentify` therefore returns immediately:
   - it shows `identify-unavailable`: "קריאה אוטומטית של המסמך אינה זמינה עדיין";
   - it offers manual entry.
5. **Validation, field mapping and identification.**
   - The downstream pipeline exists and is unit-tested:
     `identifyFromAcquisition → RegistrationExtractor → zod contract → confidence thresholds →
draft → confirm`.
   - It only ever runs with `MockRegistrationExtractor` in tests.
6. **Israeli-license parsing.** None exists. There is no OCR-text → field parser for the Israeli
   license layout; the contract expects a provider to return structured fields.
7. **Network.** None for the scan.

**Demo mode vs release build.**

- In demo mode (`EXPO_PUBLIC_DEMO_DATA=1` or UI tests), the scan uses scripted mock outcomes with a
  visible scenario picker.
- This is never active in the release/staging build.

**Classification.**

- **A**: the scan only captures a photo, then discards it.
- The reading step was **never implemented**, by design, pending gate G1.
- It is not B (no OCR is present to "not run") and not C (there is no parser).
- **D** exists only in demo mode.

**Exact reason the license is not read.** No OCR or extraction engine exists in the app.
`extractor: null` is shipped deliberately, so every capture ends at "automatic reading
unavailable".

**What works today.** Manual entry of the plate, then the consented data.gov.il lookup. It fills:

- manufacturer, model and year;
- trim and fuel;
- VIN (masked);
- and now color and engine code.

**Does a fix need a new provider, dependency or approval?** **Yes.** Every real option adds a
dependency, a native module (and therefore a new APK, not Expo Go), or an external service.
Options, smallest first:

1. **On-device OCR, plate-first (recommended).**
   - Google ML Kit on-device text recognition through a React Native/Expo module: free, offline,
     and the image never leaves the phone.
   - Read the **registration number** only, and have the user confirm it.
   - The existing consented registry lookup then fills the rest; nothing else is read from the
     image.
   - Limits to confirm in a spike: the on-device recognizer's scripts are expected **not** to
     include Hebrew, so Hebrew fields cannot be read. Digits and Latin fields (plate, VIN, engine
     code) can.
   - Needs: a dependency approval, a native build, and parsing tests on sample license photos.
2. **On-device OCR, full field extraction.** As option 1, plus a parser for the Israeli license
   layout. Blocked by the missing Hebrew recognition for the Hebrew fields. Higher effort and
   error risk.
3. **Cloud OCR/AI (vision model).**
   - Reads Hebrew, but the license image contains owner name, ID number and address.
   - This is a new external processor, a cost, and a privacy/consent decision (gate G1).
   - Not recommended for the beta.

## 5. Owner decisions (2026-09-28) and follow-up

### 5.1 Vehicle details → edit (implemented)

- **Audit.** The details card listed identity facts read-only. The only existing edit was the
  odometer (pencil → `/odometer`).
- **Implementation.** It follows the same pattern: a pencil on the details card opens
  `/vehicle/[id]/edit`, with fields for color, engine code and engine. It is not available for
  archived vehicles.
  - Empty means unknown, and nothing is derived.
  - Manufacturer, model, year and registration are **not** editable. They define the vehicle and
    its source matching, so changing them would be a separate decision.
  - The **engine is locked** while a verified schedule exists, because that schedule's exact
    applicability was proven against the current value. This is enforced in the UI and, as a
    backstop, in the store (`vehicle.engineLocked`).
  - The engine code and color are not used for applicability today, so they stay editable.
- **Domain and sync.** `updateVehicleDetails` validates like creation and bumps the version. The
  change syncs as a normal vehicle update, with field-level merge.
- **No new architecture or security decision:** the same table and repository, and no new data
  category.

### 5.2 On-device ML Kit POC: STOPPED before integration (privacy finding)

The owner's instruction: "If ML Kit integration introduces an unexpected privacy … issue, STOP and
report it before proceeding."

**Capability (current documentation, checked 2026-09-28).**

- Text Recognition v2 supports Latin, Chinese, Devanagari, Japanese and Korean. **Hebrew is not
  listed** (https://developers.google.com/ml-kit/vision/text-recognition/v2/languages).
- On-device behaviour was not measured, because nothing was integrated (see below).

**Android dependencies.**

- bundled: `com.google.mlkit:text-recognition:16.0.1`;
- or unbundled through Google Play services:
  `com.google.android.gms:play-services-mlkit-text-recognition:19.0.1`.

An Expo app needs a native module wrapper (a new dependency) and a native build.

**Privacy finding.**

- Recognition runs on-device, and the image and the recognized text are not sent.
- **However,** ML Kit's Android data disclosure
  (https://developers.google.com/ml-kit/android-data-disclosure) states that the SDK collects, and
  sends to Google over HTTPS "for diagnostics and usage analytics":
  - device information and application information;
  - **device or installation identifiers**;
  - performance metrics;
  - API configuration and input/output size;
  - feature version, event type and error codes.
- Developers report periodic uploads to `firebaselogging.googleapis.com`, and there is **no
  documented opt-out**. Google has not answered the related question in googlesamples/mlkit#1076.

**Conclusion.**

- The approved condition "the image stays on-device" would hold.
- But the integration adds a **new third-party data flow** (identifiers and usage metadata to
  Google) that the owner has not approved.
- Even the on-device POC would trigger it on the owner's phone.
- Nothing was added.

**Options for the owner:**

1. Accept the ML Kit telemetry (disclosed in the privacy notice and the Play data-safety form),
   then run the POC.
2. Run the POC with ML Kit while blocking the telemetry transport through an unofficial manifest
   change. It is unsupported by Google, may break silently, and needs a config plugin.
3. An open-source on-device engine without telemetry: Tesseract, Apache-2.0, which has Hebrew
   trained data. Larger app, slower, lower accuracy on photos; it needs a native wrapper, and
   its choice is a new dependency decision.
